# Qala Balance AI

Русскоязычный симулятор городских решений для HackAlem AI и Astana Innovations. Он помогает сравнить, как распределение ограниченного бюджета меняет показатели условных районов, и увидеть сильные стороны и компромиссы выбранного сценария.

> Все районы, начальные показатели, стоимости и эффекты в демо синтетические. Astana Quality of Life Score — результат модели сценария, а не официальный показатель и не прогноз для реальной Астаны.

## Что умеет проект

- Даёт одинаковый стартовый бюджет 1 000 млн ₸ и одинаковые исходные данные каждому сценарию.
- Требует выбрать ровно одну инициативу в каждой из пяти категорий: транспорт, озеленение, социальная инфраструктура, безопасность и городские сервисы.
- Проверяет выбор и не допускает превышение бюджета.
- Рассчитывает изменения показателей по пяти районам, результаты до и после и итоговый Score детерминированным TypeScript-кодом.
- Просит OpenAI объяснить уже посчитанный сценарий на русском языке. Модель не рассчитывает бюджет и Score.
- Возвращает содержательный детерминированный разбор, если API-ключ не задан, запрос не удался или ответ не прошёл проверку.
- При перерасходе возвращает допустимую альтернативу, найденную расчётным модулем.

## Сценарий для знакомства

Выберите следующие инициативы:

| Категория | Инициатива | Стоимость, млн ₸ |
| --- | --- | ---: |
| Транспорт | Приоритет автобусам (bus-priority) | 180 |
| Озеленение | Парки у дома (neighborhood-parks) | 170 |
| Социальная инфраструктура | Мобильные медпункты (mobile-clinics) | 130 |
| Безопасность | Безопасные переходы (safe-crossings) | 160 |
| Городские сервисы | Сервисные пункты (service-kiosks) | 120 |
| **Итого** |  | **760** |

Сценарий действителен: выбрано по одной инициативе в каждой категории, расходы не превышают бюджет 1 000 млн ₸.

Пример тела запроса к серверному анализу:

    {
      "selection": {
        "transport": "bus-priority",
        "greenery": "neighborhood-parks",
        "social": "mobile-clinics",
        "safety": "safe-crossings",
        "services": "service-kiosks"
      }
    }

## Как считается Score

Инициативы прибавляют или вычитают заданные баллы показателей только в целевых районах. После каждого эффекта показатель ограничивается диапазоном 0–100.

Сначала рассчитывается взвешенный балл каждого района:

    D_d = Σ(metric_d,k × weight_k)

Веса категорий из src/lib/scoring.ts:

| Категория | Вес |
| --- | ---: |
| Транспорт | 25% |
| Озеленение | 16% |
| Социальная инфраструктура | 24% |
| Безопасность | 20% |
| Городские сервисы | 15% |

Затем берётся обычное среднее пяти районных баллов. За разрыв между самым сильным и самым слабым районом свыше 20 пунктов применяется штраф 0,1 балла за каждый пункт превышения:

    gap = max(D_d) - min(D_d)
    penalty = max(0, gap - 20) × 0.1
    Score = round_to_1_decimal(clamp(mean(D_d) - penalty, 0, 100))

Среднее по районам в текущей модели не взвешивается по населению. Финальные значения Score ограничиваются диапазоном 0–100 и округляются до одного знака. Изменения категории и района также выдаются из расчёта симуляции.

## Архитектура

- src/data/districts.ts — пять синтетических районов и исходные показатели.
- src/data/initiatives.ts — 15 инициатив, по три на категорию, с ценой, эффектами, целевыми районами и рисками.
- src/lib/scoring.ts — веса и формула Score.
- src/lib/simulation.ts — проверка выбора и бюджета, применение эффектов, результаты до/после и поиск допустимого улучшения.
- src/lib/fallbackAnalysis.ts — воспроизводимое русскоязычное объяснение без OpenAI.
- src/app/api/analyze/route.ts — серверная проверка входных данных, повторный расчёт через simulate() и вызов OpenAI.
- src/types/simulation.ts — общий TypeScript-контракт между симуляцией, интерфейсом и API.
- src/app/ и src/components/ — интерфейс приложения.

## Как работает AI-анализ

POST /api/analyze принимает только { selection }. Сервер валидирует пять категорий, вызывает simulate() и формирует объяснение по вычисленным итогам. Клиент не может передать доверенный Score или заменить результат модели. Ответ успешного запроса имеет вид:

    {
      "analysis": {
        "summary": "...",
        "strengths": ["..."],
        "risks": ["..."],
        "tradeoffs": ["..."],
        "recommendation": "..."
      },
      "source": "openai"
    }

Если OpenAI недоступен, поле source будет fallback, а структура analysis останется такой же. Некорректное тело или набор инициатив возвращает HTTP 400. Превышение бюджета возвращает HTTP 422 и, если существует допустимая комбинация, содержит её в suggestion.

Для AI-объяснения сервер использует OpenAI Responses API со структурированным выводом. Ответ модели проверяется по контракту до передачи в интерфейс. Рекомендация остаётся привязана к рассчитанной симулятором допустимой замене. См. [официальное руководство OpenAI по Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

## Запуск локально

Нужны Node.js и npm. После интеграции интерфейса установите зависимости:

    npm install

Скопируйте пример переменных окружения:

    cp .env.example .env.local

В Windows PowerShell используйте:

    Copy-Item .env.example .env.local

Ключ API необязателен. Чтобы включить OpenAI-анализ, укажите его только в локальном файле .env.local:

    OPENAI_API_KEY=ваш_ключ
    OPENAI_MODEL=gpt-6-astra

Без OPENAI_API_KEY проект использует fallback. Файл .env.local игнорируется Git; не добавляйте секреты в исходный код, README или переменные с префиксом NEXT_PUBLIC_.

Команды проекта:

    npm run dev
    npm run lint
    npm run typecheck
    npm test
    npm run build

Откройте локальный адрес, напечатанный командой npm run dev. Точные скрипты указаны в package.json.

## Переменные окружения

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| OPENAI_API_KEY | Нет | Серверный ключ OpenAI. Без него возвращается fallback. |
| OPENAI_MODEL | Нет | Модель для объяснения; по умолчанию gpt-6-astra. |

## Ограничения и дальнейшая работа

- Районные показатели, эффекты и цены созданы для демонстрации и не являются официальными данными Астаны.
- Score показывает правила выбранной сценарной модели. Он зависит от заданных весов и синтетических эффектов и не доказывает причинный эффект в реальном городе.
- Веса, инициативы и оценки следует согласовать с городскими специалистами и калибровать на проверенных данных перед пилотом.
- Реальное внедрение потребует источников данных, регулярного обновления, проверки качества и согласования методики с Astana Innovations.
- Будущее развитие: сравнение нескольких сценариев, сохранение версий, карта воздействия и моделирование городских событий.
